# AI 科技每日简报

每天北京时间（Asia/Shanghai）09:00，在本项目根目录创建当天日期目录 `YYYY-MM-DD/`，生成中文 AI 与科技简报，再自动提交到 GitHub 仓库 [zhfk/ai-daily-bridge](https://github.com/zhfk/ai-daily-bridge) 的 `main` 分支。定时任务使用 Codex 桌面应用当前聊天中的每日任务；本地运行需要电脑开机、应用运行且项目可访问。

## 每日文件

- `YYYY-MM-DD/brief.md`：最终中文正文，保留有效来源链接，建议约 1800–2800 中文字符；字数统计不计来源 URL 和发布元数据。
- `YYYY-MM-DD/wordpress.json`：同一最终稿的发布元数据及 HTML 正文。
- `YYYY-MM-DD/images.json`：可选；新闻相关图片或可靠图片来源及署名信息。无合适图片时可省略。

日期必须在每次运行时按 Asia/Shanghai 计算，不能沿用任务创建日期。正文记录信息截止时间及采用的 24/48 小时窗口。

## 编辑要求

制作人工智能与科技每日简报。优先关注运行时刻之前最近 24 小时的重要进展，必要时扩展到 48 小时补充背景；明确区分事件发生时间与报道发布时间，避免把旧闻的新报道当作新事件。

先广泛发现候选事件，再综合重要性、影响范围、新颖性、可信度和读者价值，筛选当天最值得关注且彼此不过度重复的 5 条。发现阶段覆盖基础模型、AI Agent、OpenAI、Anthropic、Google、Meta、Microsoft、NVIDIA，以及芯片与算力、数据中心、机器人、企业 AI、融资并购、监管政策、安全、研究突破、语音/多模态等方向；最终选题不按公司配额凑数。

优先近期、可靠且尽可能一手的信息源。实际打开来源页，核查事件时间、产品可用性、数字、适用范围和来源所支持的具体事实；重大事实尽量交叉核验。官网宣布的事实与厂商自报的性能、排名或收益应分开表述。不能只凭搜索摘要、记忆或未经验证的转述撰写。

事实状态须使用以下标签并在相应陈述旁清晰说明：

- `CONFIRMED`：有适当一手依据或可靠交叉核验的事实。
- `COMPANY_CLAIM`：公司的性能、收益、排名或其他尚未独立验证的自报主张。
- `MEDIA_REPORT`：可靠媒体报道，但缺乏足够一手确认的事实。
- `UNCONFIRMED`：尚未核实的消息，明确不确定性，避免作为核心选题。
- `ANALYSIS`：编辑分析、推测、趋势判断或预测。

不得把分析、推测或预测写成已确认事实。同一条新闻可有不同状态的陈述，不应给整篇新闻一个标签后混淆其中的事实与推断。

## 正文结构

中文专业科技编辑部日报风格。开头用简洁的“今日概览 / 核心判断”，提供当日共同主线和关键信号。正文恰好 5 条新闻，每条使用简短清晰的 H2 标题；正文不得包含 H1。每条以紧凑段落或加粗字段包含：

1. 新闻摘要。
2. 必要背景 / 深度分析。
3. 为什么重要。
4. 行业趋势或潜在机会。
5. 实用信息或行动建议。
6. 事实状态。
7. 来源：保留最终稿实际使用的有效直接来源链接。

分析要有依据并明确标注；建议具体、可执行，不重复空泛表述。来源链接应支持相邻事实，保留文章或公告的直接 URL，不使用搜索结果页或内部引用 ID。未能形成 5 条可靠选题时，保留已核查资料并报告不足，不虚构事件或发布冒充合格日报的占位稿。

## 图片

如有合适视觉内容，提供与新闻直接相关的图片、图片组或可靠图片来源。优先官方事件 / 产品图片、官方公司或机构视觉素材以及可靠来源页面图片。实际打开来源后记录真实 URL、说明和署名；直接图片 URL 不可用时，只提供可靠来源页面，不猜测图片 URL。

不得使用与新闻无直接关系的泛化 AI 科技配图，不生成新闻照片。图片获取失败不得阻止日报生成。若使用 `images.json`，每项包含 `news_index`、`caption`、`source_page_url`、`credit`，以及可用时的 `image_url`；HTML/Markdown 中实际使用的图片链接保持一致。

## WordPress 发布元数据

`wordpress.json` 是发布准备文件，`tags` 为标签名称；后续发布程序可解析为 WordPress 标签 ID。字段：

- `title`：简洁文章标题，建议 20–32 个中文字符，最多 40。
- `slug`：严格为 `ai-daily-YYYY-MM-DD`，与目录日期一致。
- `excerpt`：简短中文摘要。
- `tags`：与当日选题相关的标签名称数组，去重。
- `content`：由同一份最终 `brief.md` 转换的 HTML 正文，不含 `<h1>`，5 条新闻标题使用 `<h2>`，完整保留正文、有效来源链接和实际使用的图片。

不得为 WordPress 另写一份内容不同的稿件。先定稿 Markdown，再转换 HTML，核对两者的文字和链接。

## 自动提交流程

用户已授权每日生成、提交并更新 GitHub 仓库的 `main` 分支，无需每次重复确认。

1. 在 `D:\WebstormProject\ai-daily-bridge` 生成并保存当天文件。仅处理当前日期目录，保护其他日期及用户工作。
2. 校验文件完整性、JSON 可解析、日期与 slug 一致、无 H1、恰好 5 条新闻 H2、标题长度、全部字段、事实标签、来源链接及两种正文的一致性。
3. 写作前运行 `powershell -NoProfile -File D:/WebstormProject/ai-daily-bridge/scripts/Publish-DailyBrief.ps1 -SyncOnly`，读取远程并仅通过快进同步 `main`。检查当日目录是否已存在合格完整日报；已成功发布时跳过，同一天未完成推送时优先续传已核查最终稿。
4. 完成后运行 `powershell -NoProfile -File D:/WebstormProject/ai-daily-bridge/scripts/Publish-DailyBrief.ps1 -Date YYYY-MM-DD`。脚本校验产物，仅提交当日明确指定的文件，普通推送到 `origin/main` 并核对远程提交 SHA。不会把其他已暂存文件带入提交；存在涉及其他文件的未推送提交时拒绝推送。
5. 推送若因并发更新、分支分歧、网络或认证问题失败，保留本地文件及提交，明确报告失败原因。禁止 force push、破坏性 reset、删除历史或擅自修改认证 / 安全配置。
6. 只有远程 SHA 确认成功才算完成；报告日期、文件路径和 GitHub 提交链接。脚本需要针对其准确路径的执行授权，以便定时任务能够写入 `.git` 并访问网络。

提交信息：`docs: add AI daily brief for YYYY-MM-DD`。脚本的 `-Setup` 参数只用于首次提交 `README.md` 和脚本本身。当前 GitHub 连接器创建文件返回 403，日报通过已经验证的本机 Git SSH 认证推送。

## 运行检查

完成后通知日报已生成和 GitHub 提交结果。失败时通知具体原因和已保存文件位置；不要将图片缺失当作整次任务失败。没有需要处理的新状态时保持安静，不重复汇报旧结果。
